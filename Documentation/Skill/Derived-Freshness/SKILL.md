# Derived Freshness

A diagram source renders to an SVG. A page renders to HTML. The output is
committed beside its input, so the pair can disagree.

Worked instance: a content-integrity guard requires every diagram source under a
site's content directory to have a rendered output at least as new as the source,
so a stale diagram cannot claim a stale implementation.

## The invariant

**A committed derived file is at least as new as the source it renders.**

This is the weaker of the two derivation guards, and it is worth stating
separately because it answers a question the content comparison cannot: whether
the generator was ever re-run. A diagram whose text changed and whose SVG did not
still looks like a diagram.

## The failure it prevents

A diagram's source gained a node. The SVG was not regenerated, so the rendered
page shows the old architecture - and the page is authoritative to every reader
who does not open the `.mmd`. The source and the output both exist, both are
tracked, and nothing in the build reads the source.

The same shape in a built site: a content file changed, the build output is stale,
and a reviewer opens the served page and reviews the previous content. The
comparison they are making is between the wrong two things.

## The probe

Compare modification times, source against output:

```sh
for Source in <dir>/*.mmd; do
  Output="${Source%.mmd}.svg"
  [ -f "$Output" ] || { echo "missing output: $Output"; continue; }
  [ "$Output" -nt "$Source" ] || echo "stale output: $Output"
done
```

`-nt` is true when the output is strictly newer. Equal timestamps are the common
false positive of a checkout that wrote both at once, so treat `! -nt` as
"not proven fresh" rather than as proof of staleness, and say so in the report.

## The repair

Regenerate. There is no other repair: copying the output forward without running
the generator produces a file that claims a freshness it does not have.

```sh
<generator> <source>
```

Then confirm the output changed and only in the expected way - a regeneration that
produces a byte-identical file means the source change was invisible to the
renderer, which is its own finding.

## Pitfalls

- **A fresh clone sets every mtime to the checkout time.** Freshness is a property
  of a working tree, not of a repository. In a clean clone every pair looks
  simultaneous, so the guard must either run after a build or be replaced by a
  content comparison.
- **mtime is not content.** Touching a file without changing it satisfies the
  guard; changing it and restoring the timestamp defeats it. The strong form of
  this guard is a content hash recorded beside the output - use freshness only
  where the generator is deterministic and cheap.
- **A clock skew makes a real regeneration look stale.** A file written by a
  process with a clock behind the source's write time fails the check. Compare
  with a small tolerance, or hash.
- **A build directory that is wiped between runs has no meaningful mtime.** If the
  output is gitignored and produced by the build, the guard is about the build
  having run at all - a different claim, checked by the build's own log.
- **An output that is never regenerated by anyone is not guarded by this.**
  Freshness proves the generator ran after the source; it does not prove the
  generator is the one that ships. Check that the output path is the one the
  build reads.

## Claim-to-test

| Claim | Probe | Pass condition |
| --- | --- | --- |
| Every source has an output | the loop above | no `missing output` lines |
| Every output is at least as new | `[ "$Output" -nt "$Source" ]` | true for each pair |
| Regeneration is real | run the generator, compare content | the content changed as expected |
| Freshness is meaningful here | the working tree is not a fresh clone | a build has run since checkout |
